## 工具轨迹 SFT

现有 `src/train_sft.py` 增加 `tool_trace` 目标，可加载上面生成的多轮记录；它只对 assistant 轮次计算 loss。对 7B 模型从 QLoRA 起步：

```bash
python src/train_sft.py --model /models/Qwen2.5-Math-7B-Instruct \
  --load-in-4bit --gradient-checkpointing \
  --target-mode tool_trace --data data/tool_math/train_trajectories.jsonl \
  --epochs 1 --batch-size 1 --learning-rate 0.00002 \
  --seed 5090 --output runs/tool_math_sft_qwen25math7b_seed5090_turnend
```

训练前确认 4-bit bitsandbytes kernel 在目标 5090 上可用。`tool_trace` 对 assistant 正文和每轮结束 token 计算 loss，用户题目与工具输出只作为条件上下文；旧版 `final` 与算术 `trace` 目标保持兼容。7B 训练是否能在给定序列长度和 batch 下完成，需以实测峰值显存为准。

## D/E：多轮工具 GRPO 与动态采样

`src/train_tool_grpo.py` 从轨迹 SFT adapter 初始化 4-bit NF4 基座，保留一份冻结的初始 adapter 作 KL 参考。每轮 rollout 支持 Python 工具交互，正确性奖励来自精确答案验证器；策略概率只计算模型生成的 assistant token，工具返回只进入后续上下文。rollout 默认使用 temperature=0.7、top-k=50、top-p=0.95，并在策略/reference log-prob 计算中应用同一组 logits warper，使采样分布与优化目标一致。该变换与 Transformers 4.51.3 官方 warper 在随机 logits 上逐元素相同（最大绝对差 0，保留 token 集合相同）。每组奖励做组内中心化和标准差归一化，另加 beta=0.02 的采样 KL 惩罚。当前是单次 on-policy 的 group-relative REINFORCE 更新，没有 PPO clipping，因此它是项目的 GRPO 基线实现，不等同于 TRL 旧版 `src/train.py`，也不声称复现 DAPO。

固定采样 D 每次接受预设数量的题目组；动态采样 E 在相同更新中遇到奖励全同的组时丢弃并继续抽新题，直到凑足目标有效组或达到尝试上限。丢弃组消耗的生成 token、工具调用和时间仍计入成本。可先用短 pilot 检查实现和吞吐，再增大预算：

```bash
python src/train_tool_grpo.py --model /models/Qwen2.5-Math-7B-Instruct \
  --init-adapter runs/tool_math_sft_qwen25math7b_seed5090_turnend \
  --data data/tool_math/train.jsonl --kind modular_system \
  --output runs/tool_math_grpo_fixed_modular_seed5090_v5 \
  --mode fixed --steps 5 --num-generations 4 --groups-per-step 1 \
  --max-new-tokens 192 --max-total-tokens 384 --max-tool-calls 2 \
  --learning-rate 0.000001 --beta 0.02 --temperature 0.7 --top-k 50 --top-p 0.95 \
  --seed 5090 --attn-implementation sdpa
python src/train_tool_grpo.py --model /models/Qwen2.5-Math-7B-Instruct \
  --init-adapter runs/tool_math_sft_qwen25math7b_seed5090_turnend \
  --data data/tool_math/train.jsonl --kind modular_system \
  --output runs/tool_math_grpo_dynamic_modular_seed5090_v5 \
  --mode dynamic --steps 5 --num-generations 4 --groups-per-step 1 \
  --max-attempt-groups 8 --max-new-tokens 192 --max-total-tokens 384 --max-tool-calls 2 \
  --learning-rate 0.000001 --beta 0.02 --temperature 0.7 --top-k 50 --top-p 0.95 \
  --seed 5090 --attn-implementation sdpa
```

比较 D/E 时固定 adapter 起点、种子、更新数、group size、任务池、解码参数和 token 上限。除准确率外，应比较被丢弃 rollout 的 token/时间成本、零方差组率、工具成功率、截断率与显存；仅比较更新步数会低估动态采样开销。

7B A/B/C/D/E 使用同一测试集前 9 题、few-shot 工具提示、greedy 解码和每题 1024 个生成 token 上限。D/E 从修正后的同一个 SFT adapter 开始，各做 5 个 optimizer update、group size 4，训练只用训练集中的 modular-system 题，生成上限 384 tokens，最多两次工具调用。结果如下：

| 配置 | 正确数 | 格式错误 | 平均生成 tokens | 平均工具调用 | 工具成功率 |
|---|---:|---:|---:|---:|---:|
| A 基座 direct | 7/9 | 9/9 | 764.6 | 0 | — |
| B 基座 + 工具 few-shot | 4/9 | 9/9 | 218.6 | 0.44 | 100% |
| C 工具轨迹 SFT + 工具 | 5/9 | 0/9 | 52.8 | 0.78 | 5/7 |
| D 固定采样 GRPO + 工具 | 6/9 | 0/9 | 53.7 | 0.78 | 6/7 |
| E 动态采样 GRPO + 工具 | 6/9 | 0/9 | 53.7 | 0.78 | 6/7 |

测试逐题配对上，D 和 E 的正确题目集合完全相同，均比 C 多对 1 题；A/B/C/D/E 之间的题族差异明显。各方法在计数题上均为 3/3；概率题分别为 A 3/3、B/C/D/E 1/3；同余题分别为 A 3/3、B 0/3、C 1/3、D/E 2/3。每个题族在该小测试中只有 3 题，不能将一题的变化解释为可靠提升。

配对统计中，D 相对 C 的准确率差为 +11.1 个百分点，按题目 bootstrap 的 95% percentile 区间为 [0, 33.3] 个百分点，精确 McNemar 双侧 p=1.00；E 与 D 的差为 0，区间为 [0, 0]。结果保存在 `runs/compare_grpo_fixed_vs_sft_pilot.json` 和 `runs/compare_grpo_dynamic_vs_fixed_pilot.json`。这些估计只有 9 个测试题且不包含训练种子波动，不能支持收益结论。

D 的 5 组中有 2 组包含正负奖励（40%），接受组平均 reward 为 0.10；合计生成 355 tokens、4 次工具调用、49.5 秒，峰值显存 21.63 GiB。E 为接受 5 个有奖励差异的组而尝试 17 组，丢弃 12 组（70.6%）；接受组平均 reward 为 0.50，丢弃部分消耗 972 个 token；总生成 1596 tokens、18 次工具调用、149.8 秒，峰值显存 21.68 GiB。动态采样提高了被接受组中出现奖励信号的比例，但 rollout token 约为 D 的 4.5 倍、耗时约为 3 倍；D/E 在这 9 题上得到完全相同的正确题目集合（6/9）。该 pilot 使用单个训练 seed、5 次更新、单题族采样，且 D/E 没有按相同总 rollout token 预算配平，不能证明动态采样优劣或训练后的准确率提升。

逐题评测保存在 `runs/tool_math_qwen25math7b_{direct_budget1024,tool_three_shot_budget1024,sft_tool_turnend_budget1024,grpo_fixed_modular_v5_budget1024,grpo_dynamic_modular_v5_budget1024}.jsonl`，同名 `.summary.json` 为总体指标。D/E 的 `metrics.jsonl` 记录更新、奖励方差筛选和采样成本，`rollouts.jsonl` 保存接受及丢弃轨迹、工具代码与结果。适配器权重没有提交到代码仓库。

## 外部泛化评测：MATH-500

方案要求把整数 verifier 扩展到分数、根式、元组和文字答案。`scripts/download_math500.py` 从 Hugging Face 官方 [MATH-500 数据集](https://huggingface.co/datasets/HuggingFaceH4/MATH-500) 拉取固定 revision `6e4ed1a2a79af7d8630a6b768ec859cb5af4d3be`，校验原始文件 SHA-256，并且只导出题干、gold 答案、题族标签；参考解答不会进入模型输入。本地 MATH-500 文件被 `.gitignore` 排除，manifest 保留 revision 和来源校验值。

外测使用独立的 [Math-Verify](https://github.com/huggingface/Math-Verify) `0.9.0` parser（见 `requirements-eval.txt`）。500 个 gold 中 449 个按数学表达式解析，51 个是文字答案，gold 解析失败为 0。预测优先解析最后一个完整 `\boxed{}`，再解析普通数学表达式；文字 gold 只比较最后一个完整 boxed 字面量，避免从题目推理正文中误捡到答案词。答案正确率把预测无法解析计作错误，并另报解析失败率、boxed 率、截断、工具成功率和成本。

```bash
env-grpo/bin/pip install -r requirements-eval.txt

env-grpo/bin/python src/evaluate_math500.py \

  --mode direct --max-turn-tokens 1024 --max-total-tokens 2048 \
  --output runs/math500_base_direct.jsonl
env-grpo/bin/python src/evaluate_math500.py \
  --model /root/.cache/modelscope/Qwen2.5-Math-7B-Instruct \
```

本地 TIR 提示参照 Qwen2.5-Math 官方 CoT/TIR 用法（[模型说明](https://github.com/QwenLM/Qwen2.5-Math)），Python 调用通过本项目受限计算器执行。完整外测还需注意：MATH-500 是已公开竞赛数学题，Math-7B-Instruct 可能见过其中题目；部分题含 Asymptote 图形代码，本评测仅传文本而不渲染图像。因此这项外测是公开题集上的迁移检查，不是无污染或多模态评测。

模型来自 ModelScope `master`；上游查询未提供不可变 commit id，因此将本地 Transformers 快照逐文件 SHA-256 保存在 `runs/qwen25math7b_model_manifest.json`。复现实验应先核对该 manifest，再使用匹配的模型文件。

外测 prompt pilots 只使用前 12 题。基座 direct 的 1024-token run 离线按最终 boxed 文字答案规则重评为 8/12，截断率 25%；sandbox 修正后的 TIR 在相同总预算下为 6/12，截断率 16.7%，每题平均调用 1 次工具、工具执行成功率 66.7%。修复前后 TIR 的 512-token 配对 run 都是 4/12；工具执行成功率从 40% 升到 100%，但截断率从 58.3% 升到 66.7%。这显示执行器修复增加了有效工具返回，却没有在紧预算下转化为正确答案。前 12 题的提示长度最大 819 tokens、95 分位 229 tokens，因此完整 run 的 2048 总输出预算不会被长题干挤占。以上 pilots 只用于定评测参数，不替代完整 500 题结果。

## 后续 GRPO 预算控制

为落实方案中的 D/E 等总生成 token 预算比较，`src/train_tool_grpo.py` 新增 `--rollout-token-budget`。训练在组边界检查累计 assistant 生成 token 数并停止；一个 group 不可拆开，因此实际消耗最多多出一个 group 的预算，summary 会写出超出 token 数。对比时应报告真实 token 数、耗时、optimizer update 数和动态采样丢弃率，不用设置的目标预算代替真实成本。

在修正版 3000 条全题族训练池上补做了同预算 D/E：两组从同一 SFT adapter 起步，seed 5090、group size 4、每步目标 1 组、最高 200 步、总 rollout-token 预算 10,000、每轮最多生成 192 token、每题最多两次工具调用；动态组每次更新最多尝试 8 组。首次固定采样试跑在第 8 步出现非有限 loss 并中止，未纳入比较。为稳定后续运行，采样 token 的 log-probability 下限设为 −30，参考/策略 log-ratio 在指数 KL 项前裁剪到 ±5，并在反传前检查非有限值、梯度裁剪到范数 1。5 步 smoke 和后续正式 D/E 均未再崩溃，但裁剪前梯度范数仍偶有很大值，见下表；这些稳定性处理和高梯度意味着 D/E 只能作探索性实验。

训练集由 `data/tool_math_scale_seed5090/manifest.json` 固定，`train.jsonl` 的 SHA-256 为 `56ef168bad290073d8e7f0b671390479457b0799bc6e6d2c057b22254b897e7c`。原始 D/E 的 `run_config.json` 保存了训练文件路径和 3,000 行数量，但没有数据哈希字段；后续补跑会在运行配置中记录 SHA-256。

## 扩展数据与 SFT 迭代

原 300 条版本用于工程 pilot；按方案扩大到 3000 条时，第一次审计发现随机生成产生了大量重复题和 train/validation 重叠，因此该份数据未用于训练。现版生成器按数学实例去重，并在三个 split 间拒绝重复实例。当前最终数据为 train 3000、validation 300、test 300，每类各占三分之一；3600 条题目的工具程序均通过精确 verifier，题干与实例均无重复，split 间交集为 0。数据生成 seed、各 split 和轨迹 SHA-256 保存在 `data/tool_math_scale_seed5090/manifest.json`，逐题审计保存在 `runs/tool_math_scale_seed5090_data_audit.json`。

## 旧版 Qwen3 SFT 目标诊断（待运行）

旧实验数据仍在 `data/train.jsonl`。先用固定 revision 的 Qwen3-1.7B 在旧训练题上生成一次基座回答，只把 verifier 判正确的样本放进共同训练子集；答案目标、程序校验短步骤和保留基座解答三种监督形式因而使用相同题目。保留解答的数据生成器会核对题目顺序、gold 和答案正确性，并记录过滤数与 SHA-256。

```bash
env-grpo/bin/python src/evaluate.py \
  --model Qwen/Qwen3-1.7B --data data/train.jsonl \
  --samples 1 --seed 17 --max-new-tokens 320 --batch-size 4 \
  --output runs/sft_diagnostic_base_train.jsonl

python scripts/build_preserved_reasoning.py \
  --source data/train.jsonl \
  --teacher-run runs/sft_diagnostic_base_train.jsonl \
  --common-output data/seed2027/train_base_correct_common.jsonl \
  --preserved-output data/seed2027/train_base_reasoning.jsonl \
  --audit-output runs/sft_diagnostic_teacher_audit.json

for target in final trace preserved; do
  for spec in 1e-5:0.00001 3e-5:0.00003 1e-4:0.0001; do
    label=${spec%%:*}
    lr=${spec##*:}
    if [ "$target" = preserved ]; then
      train_data=data/seed2027/train_base_reasoning.jsonl
    else
      train_data=data/seed2027/train_base_correct_common.jsonl
    fi
    env-grpo/bin/python src/train_sft.py \
      --data "$train_data" --target-mode "$target" --seed 17 \
      --epochs 1 --max-steps 32 --batch-size 4 --learning-rate "$lr" --save-steps 4 \
      --output "runs/sft_diagnostic_${target}_lr${label}"
  done
done
```

Each run saves checkpoints at steps 4, 8, 12, …, 32. Evaluate steps 4, 8, 16 and 32 on the common training subset and the unchanged original 32-question `data/validation.jsonl` using `src/evaluate.py --samples 1 --seed 17 --batch-size 4`; use the checkpoint path as `--model`, `--base-model Qwen/Qwen3-1.7B`, and pass the pinned revision from `config.json`. Name outputs `runs/sft_diagnostic_{target}_lr{label}_step{step}_{train,validation}.jsonl`, then run `scripts/summarize_sft_diagnostic.py` to collect answer accuracy, format errors and response length. This separates failure to learn the target from a train/validation gap and compares target form before interpreting learning-rate effects.
