# Qwen3 数学 RLVR 项目：流程与数据说明

本文用中文说明项目从生成数据、校准基线、训练 GRPO/SFT 到评测的完整流程。命令默认在项目根目录 `/root/llmposttraining`、已激活 `env-grpo` 环境后运行。实际脚本、依赖和结果分别见 [README](../README.md)、[RESULTS](../RESULTS.md)。

## 1. 这个实验想回答什么

实验以 Qwen3-1.7B 为基础模型，用 LoRA 做单卡 post-training，并用 Python verifier 检查数学最终答案。核心问题分成两部分：

1. 少量 GRPO 更新能否提高一组简单三步整数题的正确率？
2. 如果模型算对了却经常不遵循 `<answer>...</answer>` 格式，SFT 能否补上格式；再接 GRPO 是否能同时改善格式和正确率？

这是工程演示，不是大规模能力结论。数据只有几十到一百多道题，生成式评测有随机性，结果应看作当前配置下的观察。

## 2. 主机与运行时

主机实际检测到 1 张 NVIDIA A100-SXM4-40GB（driver 595.84，驱动报告 CUDA 13.2），16 核 CPU、约 47 GiB 内存。训练采用单卡 BF16 + LoRA，主 GRPO 峰值约 17 GiB，SFT→GRPO 峰值约 11.4 GiB。没有全参数微调或多卡。

环境隔离在项目本地 Python 3.12 Conda 环境。PyTorch 为 `2.7.1+cu128`，其余锁定版本见 `requirements.txt` 与 `requirements-lock.txt`。不要为了这组结果直接升级整套依赖。

模型页上用户最初写的 `Qwen/Qwen3-1.7B-Instruct` 不可用；项目使用可加载的 `Qwen/Qwen3-1.7B`，revision 固定在 `config.json` 中。评测和训练都关闭 Qwen3 thinking mode，以减少变量和 token 成本。

## 3. 数据怎样生成，三份数据分别做什么

运行：

```bash
python data/generate.py --seed 2026
```

生成器使用 Python `random.Random(seed)`，不依赖外部数据集或网络。每行 JSONL 有 `prompt`、`answer` 和 `kind` 三个字段。主数据切分如下：

| 文件 | 数量 | 内容 | 用途 |
|---|---:|---|---|
| `data/train.jsonl` | 128 | 三步整数符号表达式 | GRPO 和 SFT 训练 |
| `data/validation.jsonl` | 32 | 同一组符号表达式模板，不同随机操作数 | 检查初始奖励信号、诊断训练后表现 |
| `data/test.jsonl` | 48 | 工厂产量文字题，使用保留的题面模板和新的随机数值 | 固定测试集，只用于最终比较和人工抽查 |

训练/验证表达式从四种模板中随机抽取，均包含三次运算，例如：

```text
(221 + 427) * 28 - 8485
328 * 715 + 31 - 9218
(902 - 686) * 29 + 8142
```

每题的整数操作数从固定范围采样：两个主要数值为 100–999，一个乘数/批次数为 12–39，另一个数为 100–9999。生成器直接用整数运算算出 `answer`，不会让模型生成 gold。工厂题的“移除次品数”独立采样，没有约束它必须小于库存，所以部分答案会是负数；这在整数运算上正确，但现实语义不合理，是合成数据的一个限制。

测试题换成文字外壳，例如“工厂开始有多少件、每批生产多少件、生产多少批、移除多少次品，最后剩余多少”。它的底层结构仍是整数乘法、加法、减法，所以这是**题面表达迁移**，不是全新数学技能。验证集仍与训练集共享表达式模板，只换操作数；因此 validation 是同分布数值泛化检查，没有做模板隔离。

SFT→GRPO 使用另一组数据：

```bash
python data/generate.py --out data/seed2027 --seed 2027
```

该目录也生成 128/32/48 条 train/validation/test 文件。SFT→GRPO 只使用 `data/seed2027/train.jsonl` 继续训练；它有 128 个新 prompt，与 `data/train.jsonl` 不重叠。这样 GRPO 不会只在 SFT 已见过的完全相同题目上采样。它仍然与原任务共享四种符号表达式模板。

后来为了扩大评测样本，又用 seed 2028 生成了 `data/expanded_seed2028/`：256 条训练题、64 条验证题、96 条测试题。新训练 prompt 与旧 seed-2026 训练集不重叠；每个 split 内 prompt 唯一且 split 之间无重复。训练集和验证集仍是符号表达式，96 题测试仍是保留的 factory 文字题模板。这个划分规模是为后续扩展复现实验准备的，不会覆盖原来的128/32/48结果。

## 4. Verifier 如何判奖励

实现见 `src/verifier.py`。模型输出不会被 `eval` 执行，解释里的关键词或数字也不会被随便抓出来。提取规则按明确的最终答案格式执行：

1. 如果发现一个或多个可识别的 `<answer>...</answer>` 标签，只接受恰好一个且内容是数值的标签；无效或重复标签不从旁边的解释补答案。
2. 没有可识别的 answer 标签时，接受恰好一个 `\\boxed{数字}`。
3. 仍未找到时，接受独立的最后一行裸数字，或最后一行可独立验证的简单等式。
4. 将逗号、整数、小数或分数归一化成精确有理数，再与 gold 做相等比较；完全相等得 1，否则得 0。

`format_error` 单独统计是否遵守题目要求的 answer tag。因而 boxed/bare 数字可能数值正确并拿到 1 分，但仍被记为格式错误。重复 boxed 答案会被当作歧义而拒绝。

这是一种最终答案奖励，不是推理证明器：它不知道中间步骤是否正确，也无法识别猜对。20 条人工抽查没有发现错误最终数值拿到 1 分，但这不代表完整推理正确。

## 5. 基线和难度校准

训练前先在验证集做 4 次采样，避免奖励全为 0（没有组内正例）或全为 1（奖励饱和）。基线验证集 pass@1 是 71.9%，pass@4 是 81.3%，每组奖励标准差均值约 0.115，零方差组率 75%。这表示题目不是完全不会，也不是全会；但有相当部分 GRPO 组没有区分度。

初期短生成上限曾导致大量截断，因此主训练使用 max completion 320。固定测试评测每题采样 5 次，max new tokens 256。测试 pass@1 是五个随机样本中的第一个，不是 greedy；pass@5 表示五个样本任一正确。`evaluate.py` 会输出平均生成 token 数、格式错误率和每题 completion JSONL。

## 6. 主 GRPO 配置和组大小对照

直接 GRPO 的主要配置在 `config.json`：Qwen3-1.7B 固定 revision，LoRA rank 16/alpha 32，BF16，batch 8，学习率 `1e-5`，completion 上限 320，seed 17，20 个 optimizer steps。

每个 optimizer step 采 8 个 completion：

- `num_generations=4` 时，每题生成 4 个答案，因此每步有 2 个 prompt group。
- `num_generations=2` 时，每题生成 2 个答案，因此每步有 4 个 prompt group。

组大小对照保持每步 completion 总数不变，改变的是组内样本数和每步独立 prompt 数。group4 与 group2 的训练耗时都约 348 秒，峰值显存约 17 GiB。它们的 pass@1 分别为 83.3% 和 81.3%，基线为 81.3%；48 道测试题的差距很小，不能认为 GRPO 已稳定提升。

扩大版直接 GRPO 使用新训练集 256 题、40 步、group4、batch8；每个 optimizer step 仍采 8 个 completion。相较旧版，数据量和训练步数同时翻倍，因此它是一个更大规模的新 run，不是单独检验“数据量”因果效应的消融。测试评测脚本可用 `--batch-size 4` 一次批量生成四个 prompt；比较基线与训练后模型时必须保持 batch size、采样数和 token cap 一致。批量会改变采样随机数轨迹，所以和旧的逐题评测结果不做逐样本对齐。

`runs/<run>/metrics.jsonl` 按步记录 reward mean/std、零方差组比例、KL、长度、截断率、组内 token 多样性代理和显存。`group_token_entropy_bits` 是有限采样的组内 token 多样性，不是完整模型分布的熵；不同 group size 的估计有样本数偏差。

## 7. SFT 为什么试两种目标

脚本 `src/train_sft.py` 只对 assistant response 计算 loss，prompt token 的 label 设为 `-100`。基础配置为 128 条训练题、1 epoch、batch 4、LoRA、BF16、学习率 `1e-4`。

### 7.1 只监督最终答案

目标形式是：

```text
<answer>9659</answer>
```

结果：format error 降到 0%，但验证集和固定测试集 pass@1/pass@k 都是 0%。这说明模型学会了输出标签，却没有学会把新题算对。这个 adapter 没有接入最终 GRPO 链路。

### 7.2 监督程序校验的算术步骤

`--target-mode trace` 会解析生成器的简单整数表达式 AST，按运算顺序计算每一步，并确认最终值等于该行 gold；校验失败就中止训练。目标示例：

```text
Let's calculate one operation at a time.
221 + 427 = 648
648 × 28 = 18144
18144 - 8485 = 9659
<answer>9659</answer>
```

该 SFT adapter 在 validation 上 pass@1 68.8%、pass@4 71.9%、format error 0%；基线为 71.9% / 81.3%。它比只监督最终数字保留了更多算术能力，但仍未超过基线。

## 8. SFT 后接 GRPO 的实验

训练命令会先加载 trace-SFT adapter，再用 `data/seed2027/train.jsonl` 的新题做 group4、batch8、20 步 GRPO。重要实现细节是 KL reference：当 GRPO 从 SFT 开始时，脚本加载一份冻结的初始 SFT adapter 作为参考。若直接用 TRL 对 PEFT 模型默认的禁用 adapter 参考，KL 会把整个 SFT 更新都算成偏离；这次用冻结 adapter 后，KL 才衡量 RL 相对 SFT 起点的变化。

这条链路训练用时约 99 秒、显存峰值约 11.4 GiB。验证集 pass@1 为 68.8%，pass@4 为 68.8%，format error 0%。和 trace-SFT 比，pass@1 不变、pass@4 略降；格式被保留，但没有准确率收益。差异是 32 题里 1 题：SFT 的 4 个样本中有 1 个答对，GRPO 后该题 4 个样本都答错；两种模型的首样本总正确数都是 22/32。所有 128 个采样答案的正确数从 82 降到 78，差异来自第 2–4 个随机样本。78.9% 的训练组仍为零奖励方差，稀疏奖励仍是主要限制。因此未把这条链路再拿去测试集挑选，也不据此宣称 SFT→GRPO 更好。

扩大版测试集上，基线 pass@1/pass@5 为 82.3%/94.8%，40 步 GRPO 为 79.2%/93.8%；格式错误率均为100%。64题验证集上 pass@1/pass@4 则由 57.8%/75.0% 提升到 60.9%/78.1%。因此扩大验证集上的小幅提升没有转移到 96 题文字测试集；不能只挑验证结果来宣称训练有效。测试上总正确采样数从 404/480 降到 375/480，回答长度基本不变。随机抽查 20 个测试首答，17 个最终数值正确；失败中有算术误差、256-token 截断，也看到负数结果的解释存在现实语义问题。详细样例和训练日志见 `RESULTS.md`。

## 9. 如何从文件复现实验

主流程：

```bash
python data/generate.py --seed 2026
python -m unittest discover -s tests -v
python src/evaluate.py --model Qwen/Qwen3-1.7B --data data/validation.jsonl --samples 4 --seed 17 --output runs/baseline_validation.jsonl
python src/train.py --steps 20 --generations 4 --completion-length 320 --seed 17 --data data/train.jsonl --output runs/repro_grpo_g4
python src/evaluate.py --model runs/repro_grpo_g4 --base-model Qwen/Qwen3-1.7B --data data/test.jsonl --samples 5 --max-new-tokens 256 --seed 17 --output runs/repro_grpo_g4_test.jsonl
```

生成扩大版数据并复现扩大训练时，增加 split 尺寸参数；训练后比较请在两次评测里使用相同的 `--batch-size 4`：

```bash
python data/generate.py --out data/expanded_seed2028 --seed 2028 \
  --train-size 256 --validation-size 64 --test-size 96
python src/evaluate.py --model Qwen/Qwen3-1.7B \
  --data data/expanded_seed2028/test.jsonl --samples 5 --batch-size 4 \
  --max-new-tokens 256 --seed 17 --output runs/expanded_base_test.jsonl
python src/train.py --steps 40 --generations 4 --completion-length 320 \
  --seed 17 --data data/expanded_seed2028/train.jsonl \
  --output runs/expanded_grpo_g4_seed17
python src/evaluate.py --model runs/expanded_grpo_g4_seed17 \
  --base-model Qwen/Qwen3-1.7B --data data/expanded_seed2028/test.jsonl \
  --samples 5 --batch-size 4 --max-new-tokens 256 --seed 17 \
  --output runs/expanded_grpo_test.jsonl
```

SFT→GRPO 流程：

```bash
python data/generate.py --out data/seed2027 --seed 2027
python src/train_sft.py --target-mode trace --epochs 1 --batch-size 4 --learning-rate 0.0001 --seed 17 --data data/train.jsonl --output runs/repro_sft_trace
python src/train.py --steps 20 --generations 4 --completion-length 320 --seed 17 --init-adapter runs/repro_sft_trace --data data/seed2027/train.jsonl --output runs/repro_sft_grpo
python src/evaluate.py --model runs/repro_sft_grpo --base-model Qwen/Qwen3-1.7B --data data/validation.jsonl --samples 4 --max-new-tokens 256 --seed 17 --output runs/repro_sft_grpo_validation.jsonl
```

复现时使用新的输出目录，避免覆盖已有 adapter 和日志。要报告最终测试结果，应先用 validation 做决策，再固定配置跑 test；本说明里的 SFT→GRPO 只报告验证结果，因为它没有超过此前模型。

## 10. 结果能说明什么、不能说明什么

- 数据和所有验证题都属于短整数算术，不能代表多领域数学能力。
- 测试题虽然换成文字题面，底层仍是三步运算，题型迁移较浅。
- 48 个测试题、单一随机种子、五次采样不足以证明小幅指标变化有统计显著性。
- pass@5 接近饱和，不适合作为唯一指标；应同时看 pass@1 和失败样例。
- 格式奖励只看最终数值；格式错误率是单独指标。奖励正确答案不等于证明过程正确。
- 小规模 SFT 的结果对目标形式敏感：最终答案目标只教会格式；程序生成轨迹保留较多算术表现，但 SFT→GRPO 在当前 20 步预算下仍没有验证集收益。
